资讯日报订阅系统HamHome Daily Digest

多源资讯抓取、主题分栏，并定时生成可直接消费的结构化日报。

+ 速览

基于 Agent + RAG 思路的自动化资讯订阅平台，重点在于把多源信息稳定加工成可订阅、可复用、可按时送达的内容产品。

01背景与用户

使用场景适用于需要晨报、晚报、行业订阅和内部情报汇总的团队。

核心问题多源信息碎片化，人工摘要成本高，缺少稳定送达。

本轮范围以“每天按时得到可消费的主题摘要”为范围，梳理信息源、主题、时区与订阅输出；不在本轮解决深度研判和个性化推荐。

为什么做我关注的是把“读很多来源”变成“稳定收到一份结构化结果”，而不是单纯做信息抓取。

典型用户产品／运营负责人（脱敏角色）

情境
每天工作开始前，需要获取按主题和时区整理的行业摘要。
需要
在一个入口完成重点信息判断，而非在多个来源间反复切换。
风险
重复阅读与手工汇总会挤占当天的判断和协同时间。

02方案与取舍

我负责的部分我负责订阅场景梳理、主题分栏策略、摘要结构定义、定时推送机制以及结果验收口径。

关键取舍我优先输出可消费的结构化日报，而不是一次性长文总结，先保证按时送达与可复用，再逐步增强深度分析能力。

03架构与代码

触发与入口

  • Cloudflare Cron · 每 10 分钟
  • 订阅本地时间窗口判定（按时区）
  • Hono API · 手动 / 测试触发
  • Queue 生产者 → hamhome-digest

流水线 · pipeline.ts

  • 按用户读取启用的源与主题配置
  • RSS / URL 适配器抓取 · 每源限额
  • URL + 标题去重 → 当天过滤（本地日历日）
  • 主题分桶 → 重要性评审 Agent 打分
  • LLM 结构化摘要 · 失败走确定性降级

存储与投递

  • D1 (SQLite) · Drizzle ORM
  • digest_runs 记录状态 / 错误 / HTML
  • Resend 邮件 · MQTT 通知
  • Next.js 页面展示同一份结果

每一步都有「拿不到就怎么办」：源抓取失败只记错误不中断；模型打分失败走关键词 + 来源类型的确定性降级；模型漏评的条目补降级分而不是丢弃。运行状态和错误写回 digest_runs，邮件和页面读的是同一份 HTML。

我写的模块

packages/api/src/lib/pipeline.ts
主流水线：源抓取、去重、当天过滤、主题分桶、LLM 摘要与降级、邮件 / MQTT 投递、运行状态写回
packages/api/src/lib/importance-agent.ts
重要性评审 Agent：只输出 JSON 打分；模型不可用或漏评时按关键词、一手来源、内容类型确定性降级
packages/api/src/lib/schedule.ts · queue/digest-consumer.ts
按订阅者时区判定投递窗口，扫描整个 cron 间隔避免漏分钟；Queue 消费端串行跑流水线
packages/api/src/lib/topic-buckets.ts · dedup.ts · digest-recency.ts
关键词分桶与关注名单、URL + 标题去重、按本地日历日过滤
packages/db/migrations/d1/*.sql · wrangler.toml
digest_sources / runs / subscriptions 表；Workers、D1、Cron、Queues 绑定

04结果与指标

Cron 间隔
10 min
每次触发扫描整个间隔内的本地分钟，订阅者填 HH:mm 即可
摘要降级层级
3
LLM 结构化摘要 → 主题桶标题降级 → 全部标题降级，任何一层失败都有输出
内容类型权重
6
report / paper 25 · video 18 · post 16 · article 12 · news 8，一手来源再 +30
条目因模型漏评而丢失
0
normalizeReviews 对未评审条目补确定性分，再统一排序
投递通道
2
Resend 邮件 + MQTT；失败分别记入 digest_runs.error，不影响另一通道

以上为代码里的设计参数与行为，不是运营数据；订阅人数、打开率等没有公开，不写。

  • 摘要结果可复用到邮件模板与前端页面
  • 定时推送替代高频手工汇总
