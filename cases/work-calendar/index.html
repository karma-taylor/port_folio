02 & Skill 协同

项目排班协同系统Work Calendar Skill

让自然语言排班具备与网页端一致的权限、冲突规则、版本控制与审计边界。

访问上线版本 ↗查看 GitHub ↗

+ 速览

面向项目排班的网页与 Codex Skill 协同系统。核心不是让 AI 直接操作数据，而是让每一项自然语言变更都经过读取、预览、确认、服务端裁决与审计。

01背景与用户

使用场景适用于项目协调员既要在网页中查看月历，也要借助 AI 快速查询、预览和调整排班的场景。

核心问题自然语言很灵活，但排班写入必须面对人员撞期、角色权限、并发修改和隐私数据边界。

本轮范围围绕 Skill 的意图收敛、受影响日期读取、服务端预览、明确确认与 revision 写入设计闭环，不让模型承担最终业务裁决。

为什么做我把高规则密度的项目排班，推进为“系统先判断、AI 提出候选、用户确认”的人机协同模式。

典型用户项目协调员（脱敏角色）

情境
上一道工序完成后，需确认下一班组的进场安排。
需要
在确认前看清关键人员的参与区间是否已被其他工单占用。
风险
若撞期在对方确认后才发现，需要重新协调人员与进场节点。

02方案与取舍

我负责的部分我负责将排班规则建模为网页与 Skill 共享的受控 API：定义命令边界、预览与确认协议、角色权限、revision 写入，以及隐私最小化的审计方式。

关键取舍Skill 不拥有绕过规则的特权写入。它与网页端调用同一 Edge Function；身份、角色、冲突、Schema 和 revision 均由服务端裁决，安全性不依赖提示词。

  • Schema 校验 · 冲突检测
  • 预览 = dry run · 确认后 PATCH
  • expectedRevision 乐观锁 · 审计

数据

  • Postgres · apply_schedule_patch RPC
  • work_calendar_events 审计（90 天）
  • 历史快照（365 天）· 保留期清理

网页和 Skill 都不直接读写数据库表。两条入口调用同一个 Edge Function，预览与写入走同一段校验代码，只差一个 p_dry_run；因此规则不会因入口不同而分叉。

07复盘

业务痛点溯源

排班 Skill 的价值不在于替人点击，而在于让自然语言操作也遵守真实业务约束。

  • 业务约束：同一人员可分段参与多个工单，但相交的时间区间必须被阻止。
  • AI 风险：如果模型绕过当前状态、权限与冲突校验直接写入，错误会被放大为跨端协作事故。
  • 产品判断：把 AI 定位为受控操作入口，而不是拥有数据库直写权限的自动化脚本。

需求拆解与产品方案

先将自然语言收敛为可预览的单一命令，再由服务端完成业务裁决。

  • Skill 先读云端状态与expectedRevision，而非依赖用户描述推断当前排班。
  • 请求只能映射为create / update / delete之一；变更对象、人员与日期范围在预览阶段完整展开。
  • 网页与 Skill 复用同一 Edge Function，使权限、Schema、冲突和审计规则不因入口不同而分叉。

风险应对与落地交付

把模型理解转化为可拒绝、可恢复、可追责的服务端协议。

  • 预览阶段由服务端检查身份、角色、人员重叠、非法日期和分段边界；冲突不会进入写入路径。
  • 写入必须等用户明确确认；过期 revision 返回 REVISION_MISMATCH，Skill 不自动覆盖或重试。
  • 审计事件只记录角色、动作、结果、耗时和摘要；名单与原始对话不进入日志。

业务价值与验收闭环

以安全契约与可复现变更流程验收 Skill，而不用未经验证的 AI 提效数字包装结果。

  • 验收场景一：Skill 与网页端读取同一状态，且预览输出明确列出项目、人员、日期与冲突。
  • 验收场景二：越权、撞期、非法请求和过期 revision均不可写入。
  • 验收场景三：用户确认后才写入，结果可通过 revision 与审计记录复核。
