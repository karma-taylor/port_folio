01背景与用户

使用场景适用于财务、结算、运营日报与材料记录场景。

核心问题多表合并复杂、格式要求高、人工处理耗时且易返工。

本轮范围从当日 A 表、既有 B/C/D 模板和固定业务口径中梳理字段映射与异常条件；不在本轮建设通用配置平台。

为什么做这个案例体现的是我如何把重复搬数与排版，改造成可复核的自动化交付链路。

典型用户结算／运营人员（脱敏角色）

情境
日结节点前，需要把当日表、既有模板和异常条件合并为可提交日报。
需要
减少人工搬数、格式核对和反复返工，并保留异常项供复核。
风险
字段遗漏或模板口径不一致会导致日报退回，压缩后续结算时间。

02方案与取舍

我负责的部分我负责规则抽象、模板字段映射、异常校验定义、自动化流程编排以及结果验收标准制定。

关键取舍我先保证模板一致性和结果可追溯，再追求极致速度，把‘可复核’作为自动化交付的第一优先级。

03架构与代码

输入

  • 当日输入表 A（按 mm.dd 文件夹自动定位）
  • 前一日的 B / C / D 三份报表作为模板
  • 合同价格表 → 工种映射
  • location.xlsx → 地点关键词替换
  • translation_memory.csv → 人工维护词库

引擎 · daily_report_mvp.py

  • pandas 读表 · 列名归一 · 工单号规范
  • 模板固定区同步（样式 / 合并单元格 / 边框）
  • 动态区按模板行样式填充
  • 工种与作业描述规则翻译 · 最长匹配
  • 翻不出来 → exceptions 列表 · [UNMAPPED]

输出

  • B / C / D 三份当日报表（openpyxl）
  • Exceptions_YYYYMMDD.xlsx 异常清单
  • Streamlit 界面：校验输入 → 一键运行 → 日志

引擎不做 OCR、不调模型：所有翻译和映射都来自合同表、地点表和人工维护的词库，最长匹配优先；匹配不到的原样保留并进异常清单。这正是 PDF 账单 PoC 叫停后定下的范围——只做模板化、可回放的部分。

我写的模块

daily_report_mvp.py
主流程：源文件定位、读表清洗、模板固定区同步、动态区填充、样式修复、异常收集（约 1,300 行）
job_translation.py
JobSummaryTranslator：CSV 多列词库 + 默认规则，最长匹配优先的规则翻译，词库只由人工维护
report_engine.py
统一入口 run_daily_report(base_dir, template_day)：按日期推导输入 / 模板 / 输出路径，返回 ReportResult
streamlit_app.py
本地界面：选模板日、校验目录、全量或仅日报模式、运行日志与输出路径

07复盘

业务痛点溯源

日结压力不在于生成一张表，而在于多表、模板和异常条件必须同时满足提交口径。

  • 结算／运营人员在日结节点前，需要合并当日 A 表、既有 B/C/D 模板及固定业务口径。
  • 人工搬数后还要逐项核对格式、材料顺序与异常项，问题往往在提交前后反复暴露。
  • 一旦模板口径不一致或字段遗漏，日报会退回并压缩后续结算时间。

需求拆解与产品方案

将“做日报”拆解为输入口径、映射规则、模板输出与复核四个可验收环节。

  • 先做需求澄清：锁定当日表、历史模板、固定列和不可变的业务口径。
  • 再定义字段映射与清洗规则，把源数据转换为模板可消费的结构。
  • 将模板渲染、日报／台账输出和异常清单组合为一次交付，避免只完成数据加工却遗漏提交物。

风险应对与落地交付

以模板一致性和异常可追溯作为自动化交付的第一道门槛。

  • 字段缺失、规则冲突或格式不匹配时，输出明确异常而非生成看似完整但不可提交的日报。
  • 通过异常留痕保留需要人工复核的项目，使业务判断仍留在可控环节。
  • 使用模板回放验证材料顺序、格式与历史口径，降低模板变动带来的交付风险。

业务价值与验收闭环

已确认的模板回放显示：单次日报生成由约 4h 缩短至 6min。

  • 以验收指标复核输出格式、材料顺序、异常清单和模板口径是否保留。
  • 历史模板回放证明自动化输出可进入既有提交流程，而非仅生成演示样例。
  • 边界明确：当前以固定业务口径交付；规则持续膨胀时，再拆出可配置层。
